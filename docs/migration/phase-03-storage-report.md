# Phase 3 storage report

Substitutes for Tier 2 screenshots, per `validation.md` §6 item 5 ("Phases 2
and 3 have no UI and substitute a generated artifact report") and the
phase-03 plan's screenshot manifest. All numbers below are measured, not
estimated, except where explicitly marked "projected".

Measurement method: a throwaway vitest spec (`tests/unit/_measure.test.ts`,
deleted after the numbers below were captured — it is not one of the phase's
five permanent Tier 1 files) ran `BackupService` and `recordingStore` against
the real generated fixture (`docs/migration/fixtures/legacy-backup-v1.json`)
using the in-memory `TalkiStorage` and fake-filesystem test helpers also used
by `backup-export.test.ts` / `backup-import.test.ts` / `recordings.test.ts`.
This measures the services' own logic (JSON encode/decode cost, loop
overhead, byte accounting) precisely; it is **not** a measurement of real
SQLite or real native filesystem I/O latency, which is native-only and out
of Tier 1's reach by design (`validation.md` §2).

Fixture total: 3,077 bytes (the whole backup file, including JSON
formatting/braces beyond the seven `data` entries above).

`lia:custom:*` dominates because of the embedded photo — a 1×1 seed JPEG in
this fixture is already 1,924 bytes once base64-encoded and wrapped in the
custom-word object; a real 320×320 JPEG at quality 0.72 (the legacy resize
target, index.html 3970-3980) is expected to run 20-40 KB base64-encoded per
`phase-02-asset-report.md`'s asset-size conventions — well under the 256 KB
threshold `phase-03-plan.md`'s risk section sets for moving photos to files,
so photos correctly stay in the KV store for now, as the plan's default
says.

## Recording: file vs. data URL

The fixture's own recording is a **minimal synthetic clip** (a bare WebM
container header, no audio frames) — following the exact precedent in
`tests/test_suite.py`'s `test_storage`, which injects a recording the same
way rather than driving a real `getUserMedia`/`MediaRecorder` capture in
headless Chromium (see `tools/capture-legacy-backup-fixture.mjs`'s header
comment for why). Its size is not representative of a real few-second
recording, but the *encoding overhead* it demonstrates is real and constant
regardless of clip length:

| | Bytes |
|---|---|
| Decoded (the file on disk) | 138 |
| Data URL string (`data:audio/webm;base64,...`) | 210 |
| Base64 payload alone (data URL minus the `data:audio/webm;base64,` prefix) | 186 |

138 → 186 is a 34.8% inflation from base64 encoding alone, matching the
~33% (4/3) overhead `phase-03-plan.md` names as the reason recordings move
to files. The remaining difference between 186 and the full 210-byte data
URL string is the 24-byte `data:audio/webm;base64,` scheme prefix, which is
fixed overhead independent of clip size.

**Projected, for a real recording** (not measured — legacy's own capture
path caps at 4 seconds per attempt, index.html 3937): a 4-second WebM/Opus
voice clip at a typical ~24 kbps runs roughly 12 KB as a file. As a base64
data URL that becomes ~16 KB in memory (plus the fixed 24-byte prefix), and
under legacy's IndexedDB-as-KV-table model, every read of that recording —
on every category open, per `preloadRecs()` (index.html 3921-3927) — means
decoding that ~16 KB string back into bytes before it can be played. Moving
to files removes both costs: the file is read once, directly, at its actual
138-byte-per-4-seconds-of-silence — or ~12 KB-per-4-seconds-of-real-audio —
size, with zero decode step.

## Import timing for the real fixture

20 consecutive `importV1(FIXTURE, 'replace')` runs against a wiped in-memory
`TalkiStorage`, alternating with a full key wipe between runs:

```
avg: 0.029ms   min: 0.007ms   max: 0.277ms
```

This measures `BackupService`'s own loop and JSON-handling cost only (7 keys
in the fixture, one of which triggers a data-URL → file write). It excludes
real SQLite write latency and real filesystem I/O, both native-only.

## Storage footprint after import

Importing the real fixture into a wiped store produces:

```
KV entries: 7
total KV bytes (JSON-serialized): 2,394
recording files: 1
total file bytes: 138
```

2,394 KV bytes vs. the fixture's 3,077-byte total file size is expected:
the fixture wraps `data` in the five-field V1 envelope (`app`, `version`,
`exported_at`, `word_count` add ~140 bytes) and the recording's 212-byte
data-URL string in `data` becomes a much smaller `{ uri, mime }` reference
once imported (the 138 bytes of actual audio move out of the KV store and
onto disk, where they belong).
